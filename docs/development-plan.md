# 开发路线图 (Development Plan)

> **本次更新**: 2026-08-16 — 质量分层架构定型后的下一阶段路线。  
> 背景: 质量门禁（官方层）落地、双层知识库模型（platform/personal）完成、清洗管道实战修复、评估体系纠偏（GT 标注污染识别与全库重标注）。  
> 核心共识: **官方层人工标注保证质量，用户层管道自动兜底；质量评估是平台内部治理工具，不给用户展示指标。**

## 2026-08-16 路线图 — 评估闭环自动化

> 基于当日工作产出（质量门禁、双层模型、清洗修复、评估纠偏）规划的下一阶段。

### 短期（1-2 周）— 补齐评估闭环缺口

| # | 任务 | 工作量 | 依赖 | 说明 |
|---|------|--------|------|------|
| 1 | **experimenter 角色落地** | 0.5d | 无 | `get_current_experimenter_user` 依赖，eval/experiments 接口限定 admin+experimenter，三角色体系闭环 |
| 2 | **用户层管道自动体检** | 2.5d | 无 | 复用出题模块：采样 N chunk → LLM 生成问题 → 检索自测（GT=问题来源 chunk）+ 管道健康指标（清洗移除率带/粒度分布/碎片率）→ 结果只进平台质量报告，**用户不可见** |
| 3 | **官方库人工标注工具** | 2d | 无 | 标注规范（1-2 个必要 chunk、文档归属校验）+ 标注脚本/界面，解决"生成器标到术语表"类问题 |
| 4 | **门禁异步化** | 1d | 无 | Celery 任务化（第 8 个任务），官方库重建后自动触发门禁 |
| 5 | **评估数据收尾** | 1d | 3 | Python 历史 doc_id 偏差修正 + C 库人工标注 15-20 题，拿到 C 库真实基线 |

### 中期（2-4 周）— 数据驱动优化

| # | 任务 | 工作量 | 依赖 | 说明 |
|---|------|--------|------|------|
| 6 | **分块粒度研究** | 2d | 5 | C 页为何 1-2 chunks/页（HTML 标题结构保留率调查）+ 粒度消融实验（大 chunk vs 小 chunk 对 context_recall/检索精度的权衡） |
| 7 | **检索参数调优** | 1.5d | 5,6 | 基于评估数据做 α/candidate_k 网格搜索，验证 rerank 增益 |
| 8 | **质量报告增强** | 1.5d | 2,4 | 门禁历史趋势（历次结果对比）+ 全库体检汇总视图 |
| 9 | **代码质量底线** | 1d | 无 | ruff + pre-commit + 静默 except 审计（遗留项） |
| 10 | **操作日志/反馈页** | 1d | 无 | admin 查看用户反馈与操作日志（Sprint 2 遗留项） |

### 长期（1-3 月）— 生产化

| # | 任务 | 工作量 | 依赖 | 说明 |
|---|------|--------|------|------|
| 11 | **Docker 化部署** | 2d | 9 | 后端+前端+MySQL+ChromaDB+Redis 编排（遗留项） |
| 12 | **生产环境切换验证** | 3d | 11 | Milvus + PostgreSQL 配置验证（README 已声明 prod 栈） |
| 13 | **CI/CD** | 1.5d | 9 | GitHub Actions：pytest + tsc + build |
| 14 | **环境治理收尾** | 0.5d | 无 | Windows 孤儿 socket / `python3.12` 残留占显存问题的启动脚本加固（当日实测踩坑） |

### 优先级原则

1. **修复 > 功能 > 增强 > 性能** — 短期 1-2 是评估闭环核心缺口，3-5 是数据可信度基础
2. **先有真实基线再优化** — 中期 6-8 依赖短期 5 的 C 库人工标注基线
3. **评估是平台内部工具** — 用户层体检数据只进治理报告，不做用户可见功能

## 2026-07-16 版本 — 数据驱动验证（历史）

> **本次更新（当时）**: 2026-07-16 — 从"广度优先"全面转向"深度优先"。  
> 背景: v2 项目评审 (`docs/project-review-2026-07-16.md`) 指出当前项目存在"功能驱动开发、缺少数据验证闭环"的核心问题。  
> **本路线图不再罗列功能，而是按"消除不确定性"的优先级组织。**

## 核心理念

```
实现 → 测量 → 优化       ← 我们缺中间这一步
   ↕                      ← 缺了这个环，实现和优化都是盲打
优化 → 实现 → 测量
```

**三个 Sprint 的目标**:  

| Sprint | 口号 | 产出 |
|--------|------|------|
| Sprint 1 | **"现在我们知道它有效"** | RAG 四模式对比表 + SM-2 健康度报告 + 异步任务可用 |
| Sprint 2 | **"让数据可见"** | 评估前端 + A/B 实验 + 文档预览 |
| Sprint 3 | **"让学习闭环"** | SM-2 调优 + 切片增强 + 出题质量提升 |

## Sprint 1: Kill Uncertainty（7 天 · 07-17 ~ 07-23）

**目标**: 回答两个核心问题——"刚做的 BM25/Reranker 有没有用？"、"SM-2 学习系统是否正常？"

### 1.1 RAG 质量对比实验（2 天 · P0）

**为什么**: BM25 和 Reranker 花了 3 天实现，但零效果数据。不知道打开它们到底是提升还是拖慢。

**怎么做**:

| 步骤 | 任务 | 产出 |
|------|------|------|
| 1.1.1 | 扩充评估数据集至 30+ QA 对 | 覆盖 Python + Java 各 15+ 对, 含 easy/medium/hard |
| 1.1.2 | 修复 expected_chunk_ids（当前 recall 0.015 是因为 ID 设置不合理） | 每道 QA 对精准关联 1-3 个目标 chunk |
| 1.1.3 | 跑四组消融实验：Dense-only / BM25-only / Hybrid(rrf) / Hybrid+Rerank | 四组 Recall@5 / MRR / Latency 对比表 |
| 1.1.4 | 画一张对比图 | `eval_results` 表数据 → 可视化（可选） |

**验收标准**: 有一张四行四列的对比表，能回答"α=0.6 时 Rerank 比纯 RRF 提升多少"。

### 1.2 SM-2 系统审计（2 天 · P0）

**为什么**: 95 道题 + 15 条答题记录，但没人验证过排程是否正确。

**怎么做**:

| 步骤 | 任务 | 产出 |
|------|------|------|
| 1.2.1 | 审计现有 95 道题的质量 | 每题人工审查: 题干是否有歧义、错误选项是否合理、解析是否准确 |
| 1.2.2 | 统计排程状态 | `mastered` 数量、`due` 数量、`consecutive_wrong > 3` 的薄弱点、EF 分布 |
| 1.2.3 | 修复 SM-2 排程问题 | 如果 `due_date` 计算异常（如过去式/未来式大量堆积），修正算法 |
| 1.2.4 | 自动出题质量评估脚本 | 写一个脚本批量调 LLM 出题，然后用规则检查质量（选项是否有重复、答案是否在选项中、题干是否太短） |

**验收标准**: 一份 SM-2 健康度报告：95 题中多少题通过质量检查、排程分布图、薄弱点清单。

### 1.3 异步任务 E2E 验证（1 天 · P1）

**为什么**: Celery 7 个任务注册成功，但 `generate-async` 端点端口被占用时测都没测就跳过了。

**怎么做**:

| 步骤 | 任务 | 产出 |
|------|------|------|
| 1.3.1 | 确保 Redis 服务 + Celery Worker + Backend 三件套同时运行 | 稳定的本地开发环境 |
| 1.3.2 | 测试 `POST /exercises/generate-async` → 拿到 task_id | 异步提交验证通过 |
| 1.3.3 | 测试 `GET /exercises/tasks/{task_id}` → 轮询到 SUCCESS | 状态轮询验证通过 |
| 1.3.4 | 验证 task 完成后 exercises 表确实多了数据 | 数据持久化验证通过 |
| 1.3.5 | 将这三步写成 CI 脚本或 Makefile target | 可重复验证 |

**验收标准**: 一个 Makefile 脚本，`make test-async` 跑完自动验证异步出题全链路。

### 1.4 代码质量底线（1 天 · P1）

**为什么**: review 发现 `cls._tokenizer` 直接崩、`reranker` 输入污染、大量 `except: pass`。

**怎么做**:

| 步骤 | 任务 | 产出 |
|------|------|------|
| 1.4.1 | 配置 ruff（linter） + mypy（type checker） | `pyproject.toml` 中配置 |
| 1.4.2 | 修复当前所有 lint/type 错误 | 零警告通过 |
| 1.4.3 | 配置 pre-commit hook（ruff check + pytest） | 提交前自动检查 |
| 1.4.4 | 检查所有 `except: pass`，至少加 `logger.warning` | 无静默吞没 |

**验收标准**: `make lint` 零报错、`make test` 194+ 通过、pre-commit 生效。

### Sprint 1 总结

| 产出 | 验证方式 |
|------|---------|
| RAG 四模式消融对比表 | `docs/experiments/rag-ablation-2026-07.md` |
| SM-2 健康度报告 | `docs/experiments/sm2-audit-2026-07.md` |
| 异步任务验证脚本 | `make test-async` |
| 代码质量门禁 | `make lint && make test` |

## Sprint 3: Close the Learning Loop（7 天 · 07-31 ~ 08-06）

**目标**: 基于 Sprint 1 的数据，针对性地优化 SM-2 学习系统和检索质量。

### 3.1 SM-2 调优（2 天 · P1）

基于 Sprint 1 的审计结果：

| 发现问题 | 对应修复 |
|---------|---------|
| 出题质量差（题干歧义、错误选项弱） | 优化 LLM prompt，增加 few-shot 示例 |
| 排程过于激进（due_date 堆积） | 调整 SM-2 初始参数（interval/EF） |
| 薄弱点标记不准确 | 优化 `consecutive_wrong` 阈值逻辑 |
| 部分题型缺失 | 补 `code_fill` / `output_predict` 等题型 |

### 3.2 切片元数据扩展（2 天 · P2）

| 步骤 | 任务 |
|------|------|
| 3.2.1 | pipeline 分块后 LLM 生成 `summary` + `key_terms`，存入 chunk metadata |
| 3.2.2 | 按 `subject` / `language` / `difficulty` 标签分类切片 |
| 3.2.3 | BM25 启用 metadata filter，按 subject 限定检索域 |

### 3.3 检索参数调优（1 天 · P2）

基于 Sprint 1 的消融数据：

| 参数 | 调优方法 |
|------|---------|
| α (dense/sparse weight) | 网格搜索 0.1~0.9, 找最优 |
| candidate_k | 试 20/30/50, 看 recall 饱和点 |
| rerank 开关 | 确认 rerank 是否带来稳定提升 |

### 3.4 Docker 化部署（2 天 · P3）

| 步骤 | 任务 |
|------|------|
| 3.4.1 | 完善 `docker-compose.yml` — 后端 + MySQL + ChromaDB + Redis |
| 3.4.2 | 编写 DevContainer 配置 |
| 3.4.3 | 首次部署检查清单（环境变量、模型下载、数据迁移） |

## 不做清单

以下是明确 **不做** 的，防止 scope creep：

| 功能 | 理由 |
|------|------|
| ❌ 新的 LLM 提供商集成 | 当前 DeepSeek 够用，多一个提供商不会让项目更好 |
| ❌ 新的知识库导入渠道 | 文件/URL/Git 已够，再多（Notion/Confluence）只是搬运 |
| ❌ 社交/协作功能 | 单人学习工具，不需要分享/评论/协作 |
| ❌ 移动端适配 | 当前聚焦桌面端，移动端需全套 UI 重构 |
| ❌ 性能优化（大模型推理） | 99% 的性能问题在"不知道当前性能如何"，先测量再优化 |

## 长期（1-3 个月）

### P5: 间隔重复学习系统

> 这是 "RAG 切片入库即出题" 功能设想的完整形态。建议在 LEARN-1 ~ LEARN-3 验证题目质量后再启动。

#### 背景

当知识库切片入库时，让 LLM 同步完成三道工序：
1. **切片摘要 + 元数据** — 增强 RAG 检索的语义锚点
2. **配套选择题** — 按切片类型自动匹配出题（概念匹配/代码填空/输出预测/错误诊断）
3. **学习调度初始化** — 为 SSM-2 间隔重复算法准备初始参数

使每个切片同时服务于 **RAG 问答** 和 **间隔重复学习** 两个场景。

#### 完整功能规格

详见 `docs/rag-quiz-feature.md`（待创建）。

#### 依赖

| 编号 | 前置条件 |
|------|----------|
| CORE-3 | Redis/Celery 异步任务就绪（入库 LLM 调用必须异步） |
| LEARN-1 | 切片元数据扩展完成 |
| LEARN-2 | 切片类型分类完成 |
| LEARN-3 | 按需出题验证通过（确认 LLM 出题质量可接受） |
| LEARN-4 | 学习记录基础完成 |

#### 实施步骤

```
Phase 1 (2 天): 
    新增数据库表: exercises / learning_schedules / exercise_attempts
    扩展 pipeline: 分块后触发异步 LLM 生成摘要+题目
    入库时存 exercise JSON 到 metadata

Phase 2 (3 天):
    学习 API: 获取待复习题目、提交答案、更新 SM-2 排程
    前端学习页面: 题目展示、选项选择、即时反馈
    复习队列: 按 priority + due_date 排序

Phase 3 (2 天):
    学习统计面板: 每日答题数、正确率趋势、掌握切片数
    薄弱点追踪: 连续答错 3 次的切片自动标记并提升 priority
```

#### 已知风险和缓解措施

| 风险 | 缓解 |
|------|------|
| LLM 生成错误题目误导用户 | ① MVP 阶段先做 summary + key_terms，不做题目 ② 出题走按需路径（非预生成），可下线 ③ 用户可反馈题目质量 |
| 入库延迟激增 | 必须通过 Celery 异步化，同步路径不做 LLM 调用 |
| 题目质量不可控 | 连续答错率 > 60% 的题目自动冻结并告警 |
| 存储膨胀 | 单题约 1KB，10000 题仅 10MB，可接受 |
